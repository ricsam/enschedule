A schedule connects a function definition to a payload and execution policy. You create schedules from the dashboard, the CLI, or the API. Once a schedule is due, a compatible worker claims it, validates the payload, and runs the function.

## Schedule types

Enschedule supports four schedule types:

- **One-time** — runs once at the timestamp set in `runAt`.
- **Immediate** — runs as soon as a worker picks it up (`runNow: true`).
- **Recurring** — runs on a cron schedule via `cronExpression` using standard 5-field cron syntax.
- **Unscheduled** — stored but not queued; useful for templates or manual triggers.

## Create from the dashboard

1. Go to **Functions** and select the definition you want to schedule.
2. Click **Create schedule**.
3. Fill in the title, payload, and execution policy.
4. Save. The schedule appears in **Schedules** with its current status.

## Create via API

Send a `POST` request to the schedules endpoint:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key' \
  --header 'Content-Type: application/json' \
  --data '{
    "functionId": "send-receipt",
    "functionVersion": 1,
    "title": "Send receipt for order ord_123",
    "data": { "orderId": "ord_123", "email": "customer@example.com" },
    "runNow": true
  }'
```

## Use event IDs for idempotency

Set `eventId` (called `name` in the CLI) to a stable string to make schedule creation idempotent. If you submit a schedule with an `eventId` that already exists, Enschedule updates the existing record instead of creating a duplicate:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key' \
  --header 'Content-Type: application/json' \
  --data '{
    "functionId": "build-report",
    "functionVersion": 1,
    "eventId": "weekday-report",
    "title": "Weekday report",
    "data": { "accountId": "acct_123" },
    "cronExpression": "0 9 * * 1-5"
  }'
```

This pattern is safe to call on every deployment — the schedule is created once and updated in place on subsequent calls.

<Info>
  Without an `eventId`, Enschedule compares a generated signature derived from the function, run time or cron expression, and payload. An unclaimed match is returned unchanged rather than duplicated.
</Info>

## Retry failed runs

Schedules can retry automatically after a failure. Set `retries` to the number of additional attempts you want and `retryDelay` to the number of seconds to wait between attempts. You can configure both fields when creating or updating a schedule.

## Target a specific worker

Set `workerId` on a schedule to restrict execution to the worker class with that stable ID. Without it, any worker that registers the required function ID and version can claim the schedule.

## Unschedule and delete

- **Unschedule** clears the next run time and stops recurrence but keeps the schedule record and its run history intact.
- **Delete** permanently removes the schedule and all associated run records.

Both actions are available from the dashboard, the CLI, and the API.
