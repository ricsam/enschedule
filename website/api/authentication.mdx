Enschedule supports three authentication methods: an API key for service-to-service requests, JWT access and refresh tokens for user sessions, and a signed HttpOnly cookie managed automatically by the dashboard.

## API key

Use the `X-API-Key` header for service-to-service requests. The worker compares this value with the `ENSCHEDULE_API_KEY` environment variable and grants administrative access on a match.

```bash
curl https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key'
```

The API key is also accepted via the `Authorization` header using the `Api-Key` scheme:

```http
Authorization: Api-Key your-api-key
```

<Warning>
  Treat the API key as a secret. Store it in a secrets manager, send it only over HTTPS, and rotate it when exposure is suspected.
</Warning>

## User login and JWT

Exchange a username and password for access and refresh tokens:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/auth/login \
  --header 'Content-Type: application/json' \
  --data '{"username":"admin","password":"replace-me"}'
```

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ..."
}
```

Use the access token with the `Jwt` scheme on subsequent requests:

```http
Authorization: Jwt eyJ...
```

<Info>
  Access tokens expire after 15 minutes. Refresh tokens expire after seven days and rotate when used.
</Info>

## Refresh a token

Send the current refresh token to obtain a new access token and a rotated refresh token:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/auth/refresh \
  --header 'Content-Type: application/json' \
  --data '{"refreshToken":"eyJ..."}'
```

<Note>
  Persist the returned refresh token and discard the previous one. Each refresh token is single-use.
</Note>

## Log out

```bash
curl --request POST \
  --url https://enschedule.example.com/api/auth/logout \
  --header 'Content-Type: application/json' \
  --data '{"refreshToken":"eyJ...","allDevices":false}'
```

Set `allDevices` to `true` to invalidate every stored refresh session for that user across all devices.

## Dashboard session

The dashboard backend stores access and refresh tokens in a signed `HttpOnly`, `SameSite=Strict` cookie. Browser JavaScript cannot read the cookie. The backend automatically refreshes an expiring access token before forwarding API requests, so you do not need to manage token lifecycle when using the dashboard UI.
