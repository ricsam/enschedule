A function is the executable unit in Enschedule. Register it on a worker with `worker.registerJob()` inside a Bun-compatible ESM module, and Enschedule takes care of scheduling, payload validation, and result capture.

## Define a function

Create an ESM module that exports a default async `register` function. Pass each job definition to `worker.registerJob()`:

```typescript functions.ts
import { z } from "zod";

export default async function register(worker) {
  worker.registerJob({
    id: "send-receipt",
    version: 1,
    title: "Send receipt",
    description: "Email a receipt for a completed order",
    dataSchema: z.object({
      orderId: z.string().min(1),
      email: z.string().email(),
    }),
    example: {
      orderId: "ord_123",
      email: "customer@example.com",
    },
    job: async ({ orderId, email }) => {
      await sendReceipt({ orderId, email });
    },
  });
}
```

<Note>
  The module must be Bun-compatible ESM. A named `register` export is also accepted by the worker CLI in addition to the default export.
</Note>

## Definition fields

| Field | Required | Description |
| --- | --- | --- |
| `id` | Yes | Stable identifier shared by workers implementing the same function |
| `version` | Yes | Positive integer for the accepted payload and implementation version |
| `title` | Yes | Human-readable name shown in the dashboard |
| `job` | Yes | Sync or async callback that performs the work |
| `dataSchema` | No | Zod schema to validate payloads and generate JSON Schema |
| `description` | No | Explanation shown with the definition |
| `example` | No | Example payload shown to schedule authors |
| `access` | No | Who can view the function or create its schedules |
| `defaultScheduleAccess` | No | Access inherited by newly created schedules |
| `defaultRunAccess` | No | Access inherited by newly created runs |

Access policies reference immutable group keys configured by an administrator. See [Access control](/guides/access-control) for the permission matrix, inheritance rules, and complete examples.

<Note>
  Keep `id` stable across deployments. Changing it creates a different logical function and leaves existing schedules pointed at the old ID.
</Note>

## Validate payloads

Set `dataSchema` to a Zod schema. Enschedule validates each payload before the job runs and converts the schema to JSON Schema for editor validation and dashboard display. Prefer precise schemas:

```typescript
const payload = z.object({
  accountId: z.string().uuid(),
  range: z.object({
    from: z.string().datetime({ offset: true }),
    to: z.string().datetime({ offset: true }),
  }),
  format: z.enum(["csv", "json"]).default("csv"),
});
```

## Handle output and errors

Enschedule treats a completed callback as success. Throw an error to mark the run as failed:

```typescript
job: async ({ orderId }) => {
  const order = await loadOrder(orderId);
  if (!order) {
    throw new Error(`Order ${orderId} was not found`);
  }
  console.log("Processing", orderId);
}
```

All `console.log` and `console.error` output emitted during the callback is captured in the run log. Avoid logging secrets or sensitive payload fields — logs are visible to any user with access to that run.

## Version a function

Increment `version` when existing schedule payloads are not directly compatible with new code:

```typescript
worker.registerJob({
  id: "send-receipt",
  version: 2,
  title: "Send receipt",
  dataSchema: z.object({
    orderId: z.string(),
    recipient: z.object({ email: z.string().email() }),
  }),
  job: async ({ orderId, recipient }) => {
    await sendReceipt({ orderId, email: recipient.email });
  },
});
```

Existing schedules continue to reference their stored version. Register a migration when you want the worker to upgrade those payloads automatically:

```typescript
await worker.migrateHandler(
  "send-receipt",
  {
    version: 1,
    dataSchema: z.object({
      orderId: z.string(),
      email: z.string().email(),
    }),
  },
  {
    version: 2,
    title: "Send receipt",
    dataSchema: z.object({
      orderId: z.string(),
      recipient: z.object({ email: z.string().email() }),
    }),
    job: async ({ orderId, recipient }) => {
      await sendReceipt({ orderId, email: recipient.email });
    },
  },
  (data) => ({
    orderId: data.orderId,
    recipient: { email: data.email },
  }),
);
```

<Warning>
  Test migrations against production-shaped payloads before deployment. Back up PostgreSQL before any upgrade that changes stored schedules.
</Warning>
