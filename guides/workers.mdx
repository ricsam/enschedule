Workers load function definitions, publish their capabilities to PostgreSQL, and claim schedules that are ready to run. You can start a worker with the CLI or directly through the `Worker` class.

## Run with the worker CLI

Set environment variables and start the worker process:

```bash
ENSCHEDULE_WORKER_ID=mail-worker \
ENSCHEDULE_WORKER_NAME='Mail worker' \
ENSCHEDULE_WORKER_DESCRIPTION='Sends customer emails' \
ENSCHEDULE_FUNCTIONS='./functions/mail.js ./functions/reports.js' \
ENSCHEDULE_POLL_INTERVAL=10 \
ENSCHEDULE_API=true \
ENSCHEDULE_API_HOSTNAME=0.0.0.0 \
ENSCHEDULE_API_PORT=8000 \
ENSCHEDULE_API_KEY=change-me \
DATABASE_URL=postgres://user:password@db:5432/enschedule \
ENSCHEDULE_ACCESS_TOKEN_SECRET=change-me \
ENSCHEDULE_REFRESH_TOKEN_SECRET=change-me \
NAFS_URI=file:///var/log/enschedule \
bun run --cwd packages/worker-cli start
```

The worker health endpoint is available at `GET /api/healthz` once the process is running.

<Warning>
  Enabling the worker API requires `ENSCHEDULE_API_KEY`. Do not expose the worker API directly to the public internet without an authenticated gateway.
</Warning>

## Use the Worker class

For programmatic control, instantiate `Worker` directly:

```typescript worker.ts
import { Worker } from "@enschedule/worker";
import register from "./functions";

const worker = new Worker({
  workerId: "mail-worker",
  name: "Mail worker",
  accessTokenSecret: process.env.ENSCHEDULE_ACCESS_TOKEN_SECRET!,
  refreshTokenSecret: process.env.ENSCHEDULE_REFRESH_TOKEN_SECRET!,
  apiKey: process.env.ENSCHEDULE_API_KEY,
  nafsUri: process.env.NAFS_URI!,
});

await register(worker);
await worker.startPolling();
worker.serve({ port: 8000, hostname: "0.0.0.0" });
```

Call `worker.close()` during shutdown to stop polling and close the PostgreSQL connection cleanly.

## Worker identity

Each worker has two distinct identifiers:

- **`workerId`** — stable, user-provided. Use the same value for all interchangeable replicas of a worker class. A schedule with `workerId` set can only be claimed by a worker that carries that stable ID.
- **`instanceId`** — generated per process. It distinguishes individual worker registrations from one another, even when they share the same `workerId`.

A schedule without a `workerId` can be claimed by any worker that implements the required function ID and version, regardless of which worker class it belongs to.

## Scale workers

Deploy multiple replicas of the same `workerId` to increase throughput. Replicas compete to claim due schedules using `FOR UPDATE SKIP LOCKED` at the PostgreSQL level, so only one replica processes each schedule occurrence. Scale horizontally by deploying more replicas — no additional coordination is required.

## Monitor worker health

Each worker process reports its status to PostgreSQL on every poll interval:

| Status | Meaning |
| --- | --- |
| `UP` | The worker is polling and healthy |
| `PENDING` | The worker missed its expected poll window |
| `DOWN` | The worker has not polled within the configured down threshold |

A worker transitions from `UP` to `PENDING` when it misses its expected poll window, and then to `DOWN` after a configurable threshold of missed polls. Check live worker status in the dashboard under **Workers**.
