## Upgrade procedure

<Steps>
  <Step title="Back up PostgreSQL">
    Create and verify a restorable backup before changing application or database versions.
  </Step>
  <Step title="Stop or drain writers">
    Prevent older workers from writing incompatible data during the upgrade window.
  </Step>
  <Step title="Run migrations">

    ```bash
    DATABASE_URL=postgres://user:password@host:5432/database \
      bun packages/pg-driver/migrate.ts
    ```

  </Step>
  <Step title="Deploy matching components">
    Deploy dashboard and worker versions that expect the migrated schema. Keep shared package versions aligned.
  </Step>
  <Step title="Verify the system">
    Check migration output, worker registration, schedule claiming, a test run, logs, and the public health endpoint.
  </Step>
</Steps>

## Migration behavior

The migration runner:

1. Creates `drizzle.__drizzle_migrations` if needed.
2. Sorts SQL migration files by name.
3. Skips files already recorded by hash.
4. Applies each new file in a transaction.
5. Records the file only after its SQL succeeds.

The baseline migration uses existing table and column names and `IF NOT EXISTS`. This lets an existing Sequelize and Umzug database adopt the Drizzle journal without deleting application rows. Legacy migration metadata may remain in place.

<Warning>
  Idempotent SQL does not replace a backup. Always test the exact upgrade against a restored copy of production data.
</Warning>

## Breaking changes in version 2

- Bun 1.3 or later is required.
- PostgreSQL is the only supported database.
- Drizzle replaces Sequelize and Umzug in active runtime paths.
- The dashboard is a Vite React SPA with a Bun backend.
- The supported API base path is `/api`.
- The former `/api/v1` contract is removed.
- Function registration modules must be Bun-compatible ESM.
- Remix loaders and actions, Express serving, and SQLite fixtures are not supported runtime paths.

## Update function payloads

Database migrations update Enschedule's own schema. Function payload migrations are separate. Use `worker.migrateHandler()` when a new function version changes stored schedule payloads.

See [Functions](/guides/functions#version-a-function) for an example.

## Roll back

If verification fails:

1. Stop the new workers.
2. Restore the previous application images.
3. Restore PostgreSQL when the new migration is not backward compatible.
4. Verify worker and schedule health before reopening traffic.

Do not assume that rolling back a container image also rolls back the database.
