Workers load function definitions, publish their capabilities to PostgreSQL, and claim schedules that are ready to run. You can start a worker using the CLI with environment variables, or directly through the `Worker` class in your own Bun application.

## Run with the worker CLI

Set environment variables and start the worker CLI:

```bash
ENSCHEDULE_WORKER_ID=mail-worker \
ENSCHEDULE_WORKER_NAME='Mail worker' \
ENSCHEDULE_WORKER_DESCRIPTION='Sends customer emails' \
ENSCHEDULE_FUNCTIONS='./functions/mail.js ./functions/reports.js' \
ENSCHEDULE_POLL_INTERVAL=10 \
ENSCHEDULE_API=true \
ENSCHEDULE_API_HOSTNAME=0.0.0.0 \
ENSCHEDULE_API_PORT=8000 \
ENSCHEDULE_API_KEY=change-me \
DATABASE_URL=postgres://user:password@db:5432/enschedule \
ENSCHEDULE_ACCESS_TOKEN_SECRET=change-me \
ENSCHEDULE_REFRESH_TOKEN_SECRET=change-me \
NAFS_URI=file:///var/log/enschedule \
bun run --cwd packages/worker-cli start
```

The worker health endpoint is `GET /api/healthz`.

<Warning>
  Enabling the worker API requires `ENSCHEDULE_API_KEY`. Do not expose the worker API directly to the public internet without an authenticated gateway.
</Warning>

## Use the Worker class

For more control, use the `Worker` class directly in your Bun application:

```typescript worker.ts
import { Worker } from "@enschedule/worker";
import register from "./functions";

const worker = new Worker({
  workerId: "mail-worker",
  name: "Mail worker",
  accessTokenSecret: process.env.ENSCHEDULE_ACCESS_TOKEN_SECRET!,
  refreshTokenSecret: process.env.ENSCHEDULE_REFRESH_TOKEN_SECRET!,
  apiKey: process.env.ENSCHEDULE_API_KEY,
  nafsUri: process.env.NAFS_URI!,
});

await register(worker);
await worker.startPolling();
worker.serve({ port: 8000, hostname: "0.0.0.0" });
```

Call `worker.close()` during graceful shutdown to stop polling and close the PostgreSQL connection.

## Worker identity

Two identifiers distinguish workers:

- **`workerId`** — stable, user-provided. Use the same value for all replicas of the same worker class. A schedule with a matching `workerId` can only be claimed by workers with that ID.
- **`instanceId`** — generated automatically for each running process. Distinguishes individual process registrations in the dashboard.

A schedule without a `workerId` set can be claimed by any worker that registers the required `functionId` and `functionVersion`.

## Scale workers

Run multiple replicas of the same `workerId` simultaneously. Workers compete to claim due schedules using PostgreSQL's `FOR UPDATE SKIP LOCKED` — only one replica processes each schedule occurrence. Add more replicas to increase throughput without any coordination overhead.

## Monitor worker health

Each worker sends a heartbeat to PostgreSQL on every poll interval. The dashboard shows three status values under **Workers**:

| Status | Meaning |
| --- | --- |
| `UP` | Checked in within the normal polling window |
| `PENDING` | Missed the normal interval but not yet timed out |
| `DOWN` | Has not checked in before the down threshold |

The threshold includes the configured poll interval and a small grace period. A `PENDING` worker may still be alive but delayed — check its logs before assuming it has crashed.
