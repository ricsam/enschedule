Enschedule separates the code that performs work from the records that decide when that work runs. You write function definitions in your codebase and deploy workers that register them. Separately, you create schedules — in the dashboard, via the CLI, or through the API — that pair a function with a payload and an execution policy. When a schedule comes due, a worker claims it, runs the function, and writes the result to PostgreSQL as a run record. Four building blocks make this work: **function definitions**, **workers**, **schedules**, and **runs**.

## Function definition

A **function definition** describes a unit of executable code. Every definition carries:

- A stable string `id` that identifies the logical operation across deployments.
- A positive integer `version` that tracks breaking changes to the payload shape or behavior.
- A human-readable `title` displayed in the dashboard.
- An optional Zod `dataSchema` that validates the incoming payload and generates JSON Schema for dashboard forms.
- A `job` callback that receives the validated payload and executes the work.

The same function ID and version can be registered on multiple workers. Any eligible worker can claim a schedule that references that function — there is no affinity between a specific worker process and a specific function unless you explicitly target a `workerId`.

## Worker

A **worker** is a running Bun process that registers function definitions and polls PostgreSQL for due schedules. Each worker process has:

- `workerId` — a stable identifier you assign that names the worker class (for example, `email-worker`).
- `instanceId` — a value generated for the running process so each instance is individually addressable.
- A configurable poll interval that controls how frequently the worker checks for due schedules.
- A list of registered function IDs and versions the worker is prepared to execute.
- A reported status: `UP` while healthy, `PENDING` while starting, and `DOWN` once the process exits or misses heartbeats.

Workers use `SELECT ... FOR UPDATE SKIP LOCKED` when claiming due schedules. This means multiple workers can poll the same PostgreSQL table concurrently without interfering — each worker locks only the rows it is about to claim, and other workers skip those rows and move on.

## Schedule

A **schedule** connects a function ID and version to a JSON payload and an execution policy. Enschedule supports four schedule types:

- **One-time** — set `runAt` to a timezone-aware timestamp. The schedule fires once at that time.
- **Immediate** — set `runNow` to `true`. A worker claims the schedule on its next poll.
- **Recurring** — set `cronExpression`. Enschedule advances the next run time after each execution.
- **Unscheduled** — omit a future time, cron expression, and `runNow`. The schedule exists in the database but never fires automatically; you trigger it manually from the dashboard or API.

A schedule can also:

- Retry failures a configurable number of times with a delay between attempts.
- Target a specific worker class by stable `workerId`, so only that worker picks it up.
- Trigger a follow-on schedule after a failure for alerting or compensating workflows.
- Define access controls that restrict which users or API keys can view or modify its runs.

## Run

A **run** records one execution attempt of a schedule. Each run contains:

- The scheduled time the job was due.
- The actual start and finish timestamps.
- The exit status (success, failure, or timeout).
- The payload the job received.
- The worker instance that executed it.
- All log output captured during execution, viewable in the dashboard.

Retries produce additional run records for the same schedule — you can see every attempt and its outcome in the run list. A recurring schedule produces a new run record for every occurrence.

## Identity and idempotency

Every schedule has two identifiers:

- `id` — a numeric primary key generated by the database. Use it when you already have the schedule and need to reference it directly.
- `eventId` — an optional stable name you provide. When you create a schedule with an `eventId` that already exists in the database, Enschedule updates the existing schedule instead of creating a duplicate.

The `eventId` field is what makes declarative `enschedule apply` workflows idempotent. Apply the same configuration on every deployment and Enschedule converges to the desired state without accumulating duplicate schedules.

<Info>
  The CLI refers to `eventId` as the schedule **name**. Choose a value that stays stable across deployments, such as `daily-usage-report` or `weekly-invoice-sync`.
</Info>

When you create a schedule without an `eventId`, Enschedule computes a signature from the function ID, the run time or cron expression, and the payload. Submitting identical parameters a second time finds the existing schedule rather than creating a new one.

## Function versions

A schedule stores both `functionId` and `functionVersion`. A worker claims the schedule only when it has registered that exact version, or has registered a migration path from the stored version to one it supports.

Follow this rule when managing versions:

- **Increment the version** when the accepted payload shape or the observable behavior of the job changes in a way that makes old and new workers incompatible.
- **Keep the function ID stable** when you are changing the implementation but the logical operation and payload contract remain the same.

This lets you deploy updated workers alongside older ones during a rolling upgrade — old workers keep running their version while new workers pick up schedules that target the new version.
