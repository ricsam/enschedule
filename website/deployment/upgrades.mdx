Upgrading Enschedule involves updating the container images and running the database migration. The migration is idempotent — running it more than once is safe — but always take a database backup first.

## Before you upgrade

<Warning>
  Back up your PostgreSQL database before any upgrade. Enschedule migrations apply changes to live tables and cannot be automatically reversed.
</Warning>

Complete these steps before pulling new images or running `helm upgrade`:

- Take a `pg_dump` snapshot or use your cloud provider's automated backup feature
- Note the current chart or image version so you can roll back if needed
- Review the changelog for any breaking changes between your current version and the target version

## Run the database migration

### With Docker

Run the migration as a standalone container against your existing database:

```bash
docker run --rm \
  -e DATABASE_URL=postgres://user:password@host:5432/database \
  ghcr.io/ricsam/enschedule-worker:latest \
  bun packages/pg-driver/migrate.ts
```

Replace the `DATABASE_URL` value with your actual connection string before running the command.

### With Helm

Set `migration.enabled=true` in your values file. The chart runs the migration as a Kubernetes Job before the worker Deployment rolls out, so you do not need to invoke it manually:

```yaml
migration:
  enabled: true
```

## Upgrade with Helm

Pull the latest chart index, then upgrade your release with your existing values file:

```bash
helm repo update enschedule
helm upgrade enschedule enschedule/enschedule \
  --namespace enschedule \
  --values values-production.yaml \
  --wait
```

The chart's migration Job runs automatically before the worker Deployment rolls out new pods.

## Upgrade with Docker Compose

Pull the latest images and recreate the containers in one step:

```bash
docker compose pull
docker compose up -d --wait
```

If `ENSCHEDULE_MIGRATE=true` is set on the worker service, the migration runs automatically when the container starts.

## Breaking changes in 2.0

<Info>
  If you are upgrading from a 1.x release, review the following changes before proceeding:

  - **Remix, Express, Sequelize, Umzug, and SQLite were removed.** Enschedule 2 requires Bun and PostgreSQL.
  - **The supported API base path is `/api`.** The old `/api/v1` contract is no longer available.
  - **Bun and PostgreSQL are required** for both the worker and the database driver.
  - **Function registration modules must be Bun-compatible ESM.** CommonJS modules are not supported.
  - **The Drizzle-based migration uses existing table names with `IF NOT EXISTS`.** Sequelize or Umzug metadata tables left over from a previous installation remain harmlessly in place and do not need to be removed.
</Info>

## Verify after upgrade

Check that the API is healthy:

```bash
curl https://enschedule.example.com/api/healthz
```

Expected response:

```json
{"message":"Endpoint is healthy","runtime":"bun"}
```

Open the dashboard and confirm that your workers appear as `UP` and that schedules are executing as expected.
