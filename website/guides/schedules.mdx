A schedule connects a function definition to a JSON payload and an execution policy. You create schedules from the dashboard, the CLI, or the API. Once a schedule is due, a compatible worker claims it, validates the payload, and runs the function.

## Schedule types

Enschedule supports four execution policies:

| Type | How to set it | Description |
| --- | --- | --- |
| **One-time** | `runAt` | Runs once at the specified timezone-aware timestamp |
| **Immediate** | `runNow: true` | Runs as soon as a compatible worker picks it up |
| **Recurring** | `cronExpression` | Runs on a standard 5-field cron schedule |
| **Unscheduled** | _(omit all three)_ | Stored but not queued; useful for templates or manual triggers |

## Create from the dashboard

<Steps>
  <Step title="Open Functions">
    Go to **Functions** and select the definition you want to schedule.
  </Step>
  <Step title="Create a schedule">
    Click **Create schedule** and fill in the title, payload, and execution policy.
  </Step>
  <Step title="Save">
    Save the schedule. It appears in **Schedules** with its current status.
  </Step>
</Steps>

## Create via API

Send a `POST` request to `/api/schedules`:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key' \
  --header 'Content-Type: application/json' \
  --data '{
    "functionId": "send-receipt",
    "functionVersion": 1,
    "title": "Send receipt for order ord_123",
    "data": { "orderId": "ord_123", "email": "customer@example.com" },
    "runNow": true
  }'
```

## Use event IDs for idempotency

Set `eventId` to a stable string. If you create a schedule with an existing `eventId`, Enschedule updates the existing record instead of creating a duplicate. This makes deploying schedules idempotent:

```bash
curl --request POST \
  --url https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key' \
  --header 'Content-Type: application/json' \
  --data '{
    "functionId": "build-report",
    "functionVersion": 1,
    "eventId": "weekday-report",
    "title": "Weekday report",
    "data": { "accountId": "acct_123" },
    "cronExpression": "0 9 * * 1-5"
  }'
```

<Info>
  The CLI calls `eventId` the schedule **name**. Choose a value that stays stable across deployments, such as `daily-usage-report`. Without an `eventId`, Enschedule compares a generated signature (function, run time or cron, and payload) and returns an unclaimed match unchanged.
</Info>

## Retry failed runs

Schedules can retry automatically when a run fails. Set `retries` (number of additional attempts) and `retryDelay` (seconds between attempts) on the schedule. Each retry produces a separate run record.

```bash
curl --request POST \
  --url https://enschedule.example.com/api/schedules \
  --header 'X-API-Key: your-api-key' \
  --header 'Content-Type: application/json' \
  --data '{
    "functionId": "send-receipt",
    "functionVersion": 1,
    "title": "Send receipt with retries",
    "data": { "orderId": "ord_456", "email": "user@example.com" },
    "runNow": true,
    "retries": 3,
    "retryDelay": 60
  }'
```

## Target a specific worker

Set `workerId` on a schedule to restrict execution to workers with that stable ID. Without it, any worker that registers the required function ID and version can claim the schedule.

## Unschedule and delete

- **Unschedule** — clears the next run time and stops recurrence but keeps the schedule record and its run history
- **Delete** — permanently removes the schedule and all associated runs

Both actions are available from the dashboard, the CLI (`enschedule delete schedule`), and the API (`DELETE /api/schedules/:id`).
