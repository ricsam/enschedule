---
title: "Inspect and manage job execution runs in Enschedule"
sidebarTitle: "Runs"
description: "Inspect run status, captured console logs, execution timing, and retry state for every job execution from the Enschedule dashboard or API."
---

Every time a schedule is claimed and executed by a worker, Enschedule creates a run record. Runs store the start and finish times, status, captured console output, and the exact payload used — giving you complete visibility into every execution attempt.

## View runs in the dashboard

Navigate to **Runs** for a global list of all executions, or open any schedule to see runs for that schedule only. Each row shows status, start time, duration, and the claiming worker. Click a run to open its detail page, including the full captured log.

## Run statuses

| Status | Meaning |
| --- | --- |
| `RUNNING` | The run has started but has no finish timestamp yet |
| `SUCCESS` | The run finished successfully |
| `FAILED` | The run finished with an error or non-zero exit |
| `LOST` | The run has no finish timestamp and its worker is unavailable |

## Captured logs

All `console.log` and `console.error` output emitted during a job callback is stored with the run. Open the run detail page to view the full log.

<Tip>
  Avoid logging sensitive data in your job functions — logs are visible to any user with access to that run.
</Tip>

## Retries

When a schedule has retries configured, a failed run triggers another run after the configured delay. The schedule shows `RETRYING` status while waiting for the next attempt. Each retry is a separate run record — you can compare attempts on the schedule's run list to trace what changed between executions.

## View runs via API

```bash
# List all runs
curl https://enschedule.example.com/api/runs \
  --header 'X-API-Key: your-api-key'

# Get a specific run by its numeric ID
curl https://enschedule.example.com/api/runs/42 \
  --header 'X-API-Key: your-api-key'
```

## LOST runs

A run becomes `LOST` when a worker crashes or goes `DOWN` with an in-flight run. Enschedule detects this when the worker's last-seen timestamp exceeds the down threshold. A lost run does not automatically retry unless the schedule has retries configured with remaining attempts. You can view lost runs in the dashboard to decide whether to re-trigger the schedule manually.
