title: "Core concepts"
description: "Understand functions, workers, schedules, and runs in Enschedule."
---

Enschedule separates the code that performs work from the records that decide when that work runs.

## Function definition

A **function definition** describes executable code. It has a stable string `id`, a positive integer `version`, a display title, an optional Zod payload schema, and a `job` callback.

The same function ID and version can be registered on multiple workers. Any eligible worker can claim a matching schedule.

## Worker

A **worker** is a running Bun process that registers function definitions and polls PostgreSQL for due schedules. Each process has:

- a stable `workerId` that identifies the worker class
- a generated `instanceId` for the running process
- a poll interval
- a list of registered function IDs and versions
- a reported `UP`, `PENDING`, or `DOWN` status

Workers use `FOR UPDATE SKIP LOCKED` while claiming due schedules. This lets multiple workers poll concurrently without claiming the same schedule.

## Schedule

A **schedule** connects a function ID and version to a JSON payload and execution policy. It can be:

- **One-time:** set `runAt` to a timezone-aware timestamp.
- **Immediate:** set `runNow` to `true`.
- **Recurring:** set `cronExpression`.
- **Unscheduled:** omit a future time, a cron expression, and `runNow`.

A schedule can also retry failures, target a specific stable worker ID, trigger another schedule after failure, and define access for its runs.

## Run

A **run** records one execution attempt. It contains the scheduled time, start and finish times, status, payload, worker, and captured logs.

Retries produce additional runs for the same schedule. A recurring schedule also produces a run for every occurrence.

## Identity and idempotency

There are two schedule identifiers:

- `id` is the database-generated numeric ID.
- `eventId` is a caller-provided stable name.

When you create a schedule with an existing `eventId`, Enschedule updates that schedule instead of creating a duplicate. This makes declarative `enschedule apply` workflows idempotent.

<Info>
  The CLI calls `eventId` the schedule name. Choose a value that remains stable across deployments, such as `daily-usage-report`.
</Info>

Without an `eventId`, Enschedule compares a generated signature from the function, run time or cron expression, and payload. An unclaimed match is returned unchanged.

## Function versions

A schedule stores both `functionId` and `functionVersion`. A worker claims the schedule only when it has that exact version or a registered migration path from that version.

Increment the version when the accepted payload or behavior changes. Keep the function ID stable when the definition is still the same logical operation.

## Supported runtime

| Component | Supported implementation |
| --- | --- |
| Runtime and package manager | Bun 1.3+ |
| Database | PostgreSQL with Drizzle ORM |
| Dashboard | React 19 and Vite |
| API | Richie RPC at `/api` |
| API description | OpenAPI 3.1 at `/openapi.json` |
| Authentication | Signed same-origin session cookie, JWT, or API key |
